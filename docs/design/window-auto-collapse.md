# 窗口自动收进侧边 Dock

记录 WebApp 浏览器窗口「自动收进侧边刘海 Dock」的产品决策与理由。运行机制、判定条件和代码位置见 [architecture.md](../architecture.md) 的 Runtime Window Lifecycle 一节，本文不重复。

## 当前规则

窗口看不见的面积达到 **80%** 就立刻收进侧边 Dock，不再等待。

「看不见」按窗口真实露出来的面积计算，不再使用系统「还有一个像素就算可见」的粗判定：

- 被其他足够不透明的普通窗口盖住的部分
- 拖出屏幕、落在任何显示器之外的部分
- 整个窗口已经不在当前桌面（切到了别的桌面空间，或别的应用进入全屏把当前桌面占满）

调度中心、菜单栏这类系统浮层不计入遮挡——它们会让系统误报「完全看不见」，但窗口其实还在。

只排除两种：

- **最小化到程序坞**：用户主动放进坞里的，再收进侧边 Dock 是跟用户对着干。
- **窗口本就没有显示出来**（已经收进侧边 Dock，或已隐藏）：重复收起没有意义，还会放出多余的运行时状态通知。

置顶窗口不参与自动收起。正在操作的窗口（当前键盘焦点所在）也不收起。

顶部让位带双击只遵循 macOS 的系统窗口放大／还原行为，不是收起入口。不要再给它叠加双击收进侧边刘海；用户仍可使用带上明确的收起按钮。

顶部让位带只保留一个 `×`，其语义是收进侧边刘海，不是结束运行；原来的圆形收起按钮已删除。`Command W` 与 `×` 保持一致。真正结束 WebApp 只能从侧边刘海把对应图标朝屏幕中心拖过关闭门槛后松手，普通上下拖动仍只移动整块刘海。

## 决策记录

### 【裁定】2026-08-15：八成看不见立刻收起，去掉 2 秒等待

此前必须等系统报告「完全看不见」，再额外等 2 秒。机主反馈：拖一个窗口盖住大部分之后还要愣两秒才收起，体感太钝；而且只要还露出一条边，系统就永远不收。

改为：**看不见的面积达到 80% 立刻收起**。切桌面、别的应用全屏仍然一视同仁（整窗不在当前桌面 = 100% 看不见）。

2 秒等待原本是为了挡住调度中心、调度窗口这类一闪而过的系统浮层。现在这些浮层不再计入遮挡，延时失去存在理由，予以删除。**不要为了「防误触」再加回按秒计的等待。**

后续如果有人觉得「盖住一大半就收起」太敏感，先回到这条裁定，不要先把阈值改回 100% 或把延时加回去。

### 【裁定】2026-08-15：用户主动唤出后短暂不收，不是把挡住延时加回来

八成看不见立刻收起之后，从顶部刘海点已在运行的 WebApp、以及刚打开的窗口，会出现「点了没反应 / 闪一下就收进侧边栏」。根因是刚显示出来时，当前桌面的窗口列表往往还没跟上，会被算成 100% 看不见，再叠上焦点还没站稳，于是立刻收起。

两条约束：

- 当前桌面窗口列表里暂时找不到它、但系统自己还报看得见时，**不当成被挡住**。系统也报看不见（切桌面、被全屏占掉）才按完全挡住。
- 用户刚点开或从刘海 / 侧边栏唤出后，短暂忽略自动收起，让窗口有时间走到前面。过了这段仍按八成看不见立刻收。

**不要把这理解成恢复「被挡住再等两秒」。** 那条已经否决。这次只保护「用户刚刚要求看见它」这一下。

### 【裁定】2026-08-01：看不见就收起，不再区分「被盖住」和「切走了」

最初实现只认「被别的窗口盖住」，把切换桌面空间和别的应用全屏排除在外，理由是悬浮圆点设置了跨桌面显示，收起后圆点会跟着用户跑到每一个桌面空间。

机主明确推翻该取舍：**悬浮圆点的定位就是「随处可召唤」，圆点跟着用户跑是预期行为而不是副作用**。据此放开为「只要看不见就收起」。

后续如果有人觉得「切个桌面窗口就没了」不合理，先回到这条裁定，不要直接改回按桌面空间过滤。

### 【裁定】2026-08-01：散落圆点收拢为侧边刘海 Dock

每个 WebApp 独立生成悬浮圆点会让屏幕边缘越来越散乱，现统一收进一个宿主级侧边刘海。它是贴边的一整块刘海，图标直接位于刘海内部；不做悬停抽屉、二段式展开或独立拖动把手。整块刘海（包括图标区域）都可拖动，短按图标仍正常打开。圆角与贴边形状语言与顶部刘海抽屉一致，但交互形态不是抽屉。

- 设置提供左侧、右侧和底部三种明确选择。
- 首次使用自动避开系统程序坞占据的一侧；用户手动选择后，以用户设置为准。
- Dock 必须贴当前屏幕的可用边界。系统程序坞同侧时，侧边刘海停在它内侧，不能覆盖程序坞，也不能抢最外沿的唤出区域。
- 整块刘海可沿屏幕边缘上下拖动，并允许拖到其他显示器；位置按相对比例保存，分辨率变化后仍需落在可见范围内。上下两端不留死边距，可以一路拖到贴住可用区域的边缘；贴的是可用区域而不是物理屏幕边，所以底部有系统程序坞时会停在它内侧。
- **底部 Dock 是贴底的一体式刘海，不是悬浮栏**：顶部两角沿用左右贴边 Dock 的外侧圆角，底部两角沿用贴边收束弧并平滑接入屏幕边缘；底边不封成圆角，禁止做成药丸。左右贴边 Dock 保持各自既有形状，不随底部轮廓调整而变化。
- 收起列表跨桌面空间可见，点开条目后由对应运行时把原窗口带到用户当前桌面。

#### 【裁定】2026-09-01：网页应用窗口不得挡住本应用的侧边 Dock

这里说的是 NeatWebApp 自己的侧边刘海，不是系统程序坞。系统 `visibleFrame` 只避开了程序坞和菜单栏，侧边 Dock 贴在这块可用区域的内侧，所以网页窗口按可用桌面铺开或拖到贴边时，会落到 Dock 底下。Dock 又是通透玻璃，窗口内容会透上来，看起来就像挡住了。

规则：

- **有收纳图标、Dock 正在显示时**，该屏上网页窗口的可用区域是 `visibleFrame` 再扣掉 Dock 所在那条边的整条厚度。左右扣宽度，底部扣高度。矩形窗口挖不出刘海缺口，所以预留的是整条边，不是只避开当前那一小段面板。
- **Dock 没有显示时不扣**。没有收纳的网页应用时侧边刘海是收起来的，窗口仍可用完整 `visibleFrame`。
- 只扣 Dock 当前所在的那块屏；其他显示器保持原 `visibleFrame`。
- 启动盖和真窗必须按同一块可用区域算框，否则又会对不齐。
- 用户拖动、缩放、双击放大，以及别的窗口被收进 Dock 之后新出现的刘海，都要继续避开。已经压住预留条的窗口立刻让开，不要等下次拖动。

**不要**靠把玻璃做成不透明、或把 Dock 窗口层级抬到异常高，来「盖过」已经压上来的网页窗口。通透玻璃是已裁定的外观；挡住是几何问题，按可用区域约束窗口。也不要把侧边 Dock 降到普通窗口下面好让用户把窗口拖上去。

#### 【裁定】2026-08-16：顶部刘海和侧边栏图标必须单击即开

机主反馈这两处图标单击没反应，只有连点两下才打开。

两条根因要同时保住，修一条留一条会再复发：

1. 两块都是非激活浮层。系统默认把第一次按下用来「点亮窗口」，图标手势看不到这次点击。必须让图标直接吃掉第一次按下，不能指望用户先点一下再点一下。
2. 点开和拖动共用同一条按下手势。触控板单击经常带几像素抖动；位移门槛过低时，单击会被当成拖动，松手后点开被丢掉。点开与拖动的分界必须宽到能容下单击抖动（当前按八像素），并且只有真正开始拖过之后才短暂忽略随后的点开。

**不要把位移门槛再降回「几乎零抖动才算点开」。** 也不要把点按和拖动拆成两条并行手势——拖动手势会把点按吃掉。

#### 【裁定】2026-08-16：侧边 Dock 改用通透液态玻璃（推翻「标准玻璃」）

此前选标准玻璃，是怕只有五十多点宽的贴边条在浅色壁纸上会「看不见底板」。真机对照快捷捕捉窗之后，标准玻璃看起来是一层雾面，不是液态玻璃：没有折射、没有通透感。

机主明确要求侧边 Dock 与快捷捕捉窗使用同一套通透玻璃。Dock 上只有图标、没有成段文字，可读性不靠整块雾面来兜。低于 macOS 26 的系统仍退回纯黑底板加细描边；贴边形状不变。

**不要再把侧边 Dock 退回标准玻璃 / 雾面材质来「增加存在感」。** 存在感来自折射和高光，不是来自把玻璃做成毛玻璃。

#### 【裁定】2026-08-01：底板材质改为系统液态玻璃

侧边刘海底板由纯黑改成 macOS 26 的系统液态玻璃，低于 macOS 26 的系统仍退回纯黑底板加细描边，两条路径共用同一套形状与圆角。通透/标准的选择以 2026-08-16 裁定为准。

- 侧边刘海是非激活面板，绝大多数时间既不是 key 也不是 main。系统会把非活跃窗口上的玻璃压暗成灰调，必须在面板层显式声明活跃外观，否则玻璃长期停在灰暗状态。
- 底板不再恒为深色，图标的键盘焦点圈必须用随明暗自适应的前景色，不能写死白色。
- **玻璃不产生可命中的像素**：底板从纯黑换成玻璃后，图标以外的区域在系统看来是全透明的，按下事件会直接穿透到下层窗口，表现为「整块 Dock 只有图标能拖」。必须在玻璃形状上再垫一层极低不透明度的实色兜住命中区域。同理，图标放得下时不要套滚动容器——滚动容器会吞掉整块 Dock 的拖动手势。

> 上面几条里的通用部分（清透/标准玻璃变体怎么选、非激活窗口玻璃被压暗怎么修、玻璃不产生可命中像素、低于 26 的降级路径与形状共用、通透玻璃的私有属性隔离）已上收为工作区通用规范，见 [液态玻璃跨平台实践](../../../../_standards/workspace-docs/swift-docs/liquid-glass-practices.md)。本节保留本项目的裁定与具体参数。

#### 【裁定】2026-08-01：关闭手势必须是横向为主

沿屏幕边缘上下拖动时，手会自然朝屏幕内侧偏，旧实现只看「朝内走了多远」且取整个手势过程的最大值，导致上下调整位置时经常误关 WebApp。

- 只有横向位移大于纵向位移的拖动才算关闭手势；纵向占主导时一律当作调整位置。
- 以松手那一刻的位移判定，中途偏出去再拉回来不算关闭。
- 位移必须用屏幕坐标测量：Dock 会跟着光标移动，窗口内坐标系本身在动，量出来的不是用户真实位移。

### 【裁定】2026-08-01：删除闲置超时收起

此前另有一条规则：窗口失去焦点满 3 分钟自动收起。机主判断「看不见就收起」已完全覆盖其价值，超时收起纯属多余，予以删除。

**不要再加回任何形式的闲置超时收起。** 看得见的窗口，用户放着多久不动都不应该自己缩掉——窗口还在视野里却突然消失，是比「忘了关」更差的体验。

### 【裁定】2026-08-01：删除窗口分身

此前浏览器顶栏有「复制为新窗口」按钮，可以把同一个 WebApp 开成多个窗口。机主判断该功能不常用且本身有缺陷，予以删除，并连同底层能力一起清理（不是只藏按钮）。

现在每个运行时进程严格只拥有一个窗口。不要再引入同一 WebApp 多窗口的能力。

## 为什么必须做「窗口跟随用户所在桌面」

侧边 Dock 在所有桌面空间都点得到，但窗口默认只属于它被创建时的那个桌面空间。放开「切桌面也收起」之后，「从别的桌面点 Dock 唤回窗口」从边缘情况变成日常操作，而 macOS 的默认行为是把**用户**拽回窗口所在的桌面空间——与 Dock「随处可召唤」的定位完全相反。

因此窗口必须带上 `.moveToActiveSpace`。删掉这个属性，这次改动的净体验是负的。

## 踩过的坑

### 自动收起会把焦点抢给一个早已不在前台的旧应用

收起流程末尾会「把焦点还给上一个前台应用」，而这个记录是在用户主动唤起窗口时写下的，到自动收起时早已过期。

例：用户从访达唤起 WebApp（记下访达）→ 切去 Safari → Safari 盖住窗口触发自动收起 → 焦点被从 Safari 抢走丢回访达。

**收起前必须先刷新一次「上一个前台应用」**，让它指向当前真正在前台的那个，这样归还焦点才是无害的空操作。新增任何自动收起触发路径时都要保证这一步。

### 系统的「完全看不见」比直觉宽，且不够用

- 系统 `occlusionState` 只要还露出一个像素就报「可见」，不能拿来做「盖住一大半就收起」。遮挡比例必须按窗口列表做矩形差集：先裁掉屏幕外的部分，再扣掉位于前面、同一层级、足够不透明的窗口。重叠的遮挡窗口不能把重叠部分算两次。
- 调度中心、菜单栏等高层级浮层必须忽略。以前靠 2 秒延时去抖；延时删掉之后，漏掉这一层过滤会让窗口在调出调度中心时自己缩掉。
- 切桌面时窗口不会出现在当前桌面的窗口列表里，按 100% 看不见处理，与「被盖住」仍然一视同仁。
- 状态会在失去焦点、切应用、切桌面时变化，收起前必须**重新判定一次**，不能相信稍早捕获的状态。
- `NSWindow.isVisible` 为 false 同时涵盖「最小化」和「已被移出屏幕」两种情况，不要指望用它单独区分这两者。

参考：[occlusionState](https://developer.apple.com/documentation/appkit/nswindow/occlusionstate-swift.property)（只区分全遮 / 还剩一像素，没有比例）· [CGWindowListCopyWindowInfo](https://developer.apple.com/documentation/coregraphics/cgwindowlistcopywindowinfo(_:_:)) · [moveToActiveSpace](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct/movetoactivespace)

## 真机验收清单

1. **立刻收起**：用另一个窗口盖住 WebApp 大约八成，应马上收进侧边 Dock，不再愣一两秒。
2. **还露着一大块就别收**：只盖住一半或露出超过两成时，窗口应留在原地。
3. **调度中心不误收**：调出调度中心再退回，窗口应还在，不能自己缩进 Dock。
4. **跨桌面唤回**：在别的桌面点 Dock 条目，窗口应当来到用户当前桌面，而不是把用户拽回原桌面。
5. **别的应用全屏时点 Dock**：Dock 本身能浮在全屏应用之上。但 macOS 通常不允许把普通窗口放进别的应用的全屏空间，点开大概率会切出全屏。**这是系统限制，不是缺陷**；如果实测体感不可接受，需要单独设计兜底方案，不要简单回退本次改动。
6. **收起后焦点归属**：确认没有把焦点从用户正在用的应用抢走。
7. **置顶窗口**：确认全程不会被自动收起。
8. **系统程序坞同侧**：系统程序坞在右侧时，把侧边 Dock 也切到右侧，确认它停在程序坞内侧且不影响程序坞唤出。
9. **拖动与多屏**：沿边缘拖动、拖过拐角换边（左/右 ↔ 底），并跨屏，重启后确认仍在正确屏幕、贴边和相对位置。上边不应被贴上。
10. **焦点表现**：启动、鼠标点击和键盘导航时都不出现系统蓝色焦点框；键盘聚焦条目时仍能看到克制的自定义焦点态。
11. **刘海点已开的应用**：窗口已收进侧边栏或在别的窗口后面时，从顶部刘海再点一次应唤到前面，不能秒关或没反应。
12. **刚打开不秒关**：新开一个 WebApp，窗口应留在前面，不能闪一下就收进侧边栏。
13. **单击即开**：别的应用仍在前台时，单击顶部刘海图标和侧边栏图标各一次，都应打开对应网页应用；连点不是必经路径。
14. **窗口不挡侧边 Dock**：侧边栏里已有收纳图标时，把一个网页窗口拖到或放大到同一侧贴边，窗口应停在 Dock 内侧，不能压住刘海。再收起另一个网页应用让 Dock 出现时，已经贴边的窗口也应立刻让开。没有收纳图标时，窗口仍可铺满系统可用桌面。
