# 窗口自动收进侧边 Dock

记录 WebApp 浏览器窗口「自动收进侧边刘海 Dock」的产品决策与理由。运行机制、判定条件和代码位置见 [architecture.md](../architecture.md) 的 Runtime Window Lifecycle 一节，本文不重复。

## 当前规则

窗口只要被系统判定为「看不见」，持续 2 秒就自动收进侧边 Dock。

「看不见」采纳系统 `NSWindow.occlusionState` 的判定，包含三种情形，全部一视同仁：

- 被其他不透明窗口完全盖住
- 用户切到了别的桌面空间
- 别的应用进入全屏

只排除两种：

- **最小化到程序坞**：用户主动放进坞里的，再收进侧边 Dock 是跟用户对着干。
- **窗口本就没有显示出来**（已经收进侧边 Dock，或已隐藏）：重复收起没有意义，还会放出多余的运行时状态通知。

置顶窗口不参与自动收起。

顶部让位带双击只遵循 macOS 的系统窗口放大／还原行为，不是收起入口。不要再给它叠加双击收进侧边刘海；用户仍可使用带上明确的收起按钮。

顶部让位带只保留一个 `×`，其语义是收进侧边刘海，不是结束运行；原来的圆形收起按钮已删除。`Command W` 与 `×` 保持一致。真正结束 WebApp 只能从侧边刘海把对应图标朝屏幕中心拖过关闭门槛后松手，普通上下拖动仍只移动整块刘海。

## 决策记录

### 【裁定】2026-08-01：看不见就收起，不再区分「被盖住」和「切走了」

最初实现只认「被别的窗口盖住」，把切换桌面空间和别的应用全屏排除在外，理由是悬浮圆点设置了跨桌面显示，收起后圆点会跟着用户跑到每一个桌面空间。

机主明确推翻该取舍：**悬浮圆点的定位就是「随处可召唤」，圆点跟着用户跑是预期行为而不是副作用**。据此放开为「只要看不见就收起」。

后续如果有人觉得「切个桌面窗口就没了」不合理，先回到这条裁定，不要直接改回按桌面空间过滤。

### 【裁定】2026-08-01：散落圆点收拢为侧边刘海 Dock

每个 WebApp 独立生成悬浮圆点会让屏幕边缘越来越散乱，现统一收进一个宿主级侧边刘海。它是贴边的一整块刘海，图标直接位于刘海内部；不做悬停抽屉、二段式展开或独立拖动把手。整块刘海（包括图标区域）都可拖动，短按图标仍正常打开。圆角与贴边形状语言与顶部刘海抽屉一致，但交互形态不是抽屉。

- 设置提供左侧、右侧和底部三种明确选择。
- 首次使用自动避开系统程序坞占据的一侧；用户手动选择后，以用户设置为准。
- Dock 必须贴当前屏幕的可用边界。系统程序坞同侧时，侧边刘海停在它内侧，不能覆盖程序坞，也不能抢最外沿的唤出区域。
- 整块刘海可沿屏幕边缘上下拖动，并允许拖到其他显示器；位置按相对比例保存，分辨率变化后仍需落在可见范围内。上下两端不留死边距，可以一路拖到贴住可用区域的边缘；贴的是可用区域而不是物理屏幕边，所以底部有系统程序坞时会停在它内侧。
- **底部 Dock 是贴底的一体式刘海，不是悬浮栏**：顶部两角沿用左右贴边 Dock 的外侧圆角，底部两角沿用贴边收束弧并平滑接入屏幕边缘；底边不封成圆角，禁止做成药丸。左右贴边 Dock 保持各自既有形状，不随底部轮廓调整而变化。
- 收起列表跨桌面空间可见，点开条目后由对应运行时把原窗口带到用户当前桌面。

#### 【裁定】2026-08-01：底板材质改为系统液态玻璃

侧边刘海底板由纯黑改成 macOS 26 的系统液态玻璃（`glassEffect` 配合贴边形状），低于 macOS 26 的系统仍退回纯黑底板加细描边，两条路径共用同一套形状与圆角。

- 采用标准玻璃而非全透明玻璃：Dock 只有 54pt 宽，全透明玻璃在浅色背景下几乎看不见底板，失去「一块可拖动实体」的感知。
- 侧边刘海是非激活面板，绝大多数时间既不是 key 也不是 main。系统会把非活跃窗口上的玻璃压暗成灰调，必须在面板层显式声明活跃外观，否则玻璃长期停在灰暗状态。
- 底板不再恒为深色，图标的键盘焦点圈必须用随明暗自适应的前景色，不能写死白色。
- **玻璃不产生可命中的像素**：底板从纯黑换成玻璃后，图标以外的区域在系统看来是全透明的，按下事件会直接穿透到下层窗口，表现为「整块 Dock 只有图标能拖」。必须在玻璃形状上再垫一层极低不透明度的实色兜住命中区域。同理，图标放得下时不要套滚动容器——滚动容器会吞掉整块 Dock 的拖动手势。

> 上面四条里的通用部分（清透/标准玻璃变体怎么选、非激活窗口玻璃被压暗怎么修、玻璃不产生可命中像素、低于 26 的降级路径与形状共用）已上收为工作区通用规范，见 [液态玻璃跨平台实践](../../../../_standards/workspace-docs/swift-docs/liquid-glass-practices.md)。本节保留本项目的裁定与具体参数。

#### 【裁定】2026-08-01：关闭手势必须是横向为主

沿屏幕边缘上下拖动时，手会自然朝屏幕内侧偏，旧实现只看「朝内走了多远」且取整个手势过程的最大值，导致上下调整位置时经常误关 WebApp。

- 只有横向位移大于纵向位移的拖动才算关闭手势；纵向占主导时一律当作调整位置。
- 以松手那一刻的位移判定，中途偏出去再拉回来不算关闭。
- 位移必须用屏幕坐标测量：Dock 会跟着光标移动，窗口内坐标系本身在动，量出来的不是用户真实位移。

### 【裁定】2026-08-01：删除闲置超时收起

此前另有一条规则：窗口失去焦点满 3 分钟自动收起。机主判断「看不见就收起」已完全覆盖其价值，超时收起纯属多余，予以删除。

**不要再加回任何形式的闲置超时收起。** 看得见的窗口，用户放着多久不动都不应该自己缩掉——窗口还在视野里却突然消失，是比「忘了关」更差的体验。

### 【裁定】2026-08-01：删除窗口分身

此前浏览器顶栏有「复制为新窗口」按钮，可以把同一个 WebApp 开成多个窗口。机主判断该功能不常用且本身有缺陷，予以删除，并连同底层能力一起清理（不是只藏按钮）。

现在每个运行时进程严格只拥有一个窗口。不要再引入同一 WebApp 多窗口的能力。

## 为什么必须做「窗口跟随用户所在桌面」

侧边 Dock 在所有桌面空间都点得到，但窗口默认只属于它被创建时的那个桌面空间。放开「切桌面也收起」之后，「从别的桌面点 Dock 唤回窗口」从边缘情况变成日常操作，而 macOS 的默认行为是把**用户**拽回窗口所在的桌面空间——与 Dock「随处可召唤」的定位完全相反。

因此窗口必须带上 `.moveToActiveSpace`。删掉这个属性，这次改动的净体验是负的。

## 踩过的坑

### 自动收起会把焦点抢给一个早已不在前台的旧应用

收起流程末尾会「把焦点还给上一个前台应用」，而这个记录是在用户主动唤起窗口时写下的，到自动收起时早已过期。

例：用户从访达唤起 WebApp（记下访达）→ 切去 Safari → Safari 盖住窗口触发自动收起 → 焦点被从 Safari 抢走丢回访达。

**收起前必须先刷新一次「上一个前台应用」**，让它指向当前真正在前台的那个，这样归还焦点才是无害的空操作。新增任何自动收起触发路径时都要保证这一步。

### 系统的「看不见」比直觉宽，且是异步更新的

- 判定必须用位掩码（`occlusionState.contains(.visible)`），不能用等号比较。
- 调度窗口、调出 Mission Control 这类一闪而过的动作都会瞬间报告「看不见」，不做延迟去抖会出现窗口莫名自己缩掉的抽风感。
- 状态异步更新，收起延时到点后必须**重新判定一次**，不能相信排程那一刻捕获的状态。
- `NSWindow.isVisible` 为 false 同时涵盖「最小化」和「已被移出屏幕」两种情况，不要指望用它单独区分这两者。

## 真机验收清单

1. **2 秒延时的手感**：是否够快、是否还会被瞬时动作误触发。
2. **跨桌面唤回**：在别的桌面点 Dock 条目，窗口应当来到用户当前桌面，而不是把用户拽回原桌面。
3. **别的应用全屏时点 Dock**：Dock 本身能浮在全屏应用之上。但 macOS 通常不允许把普通窗口放进别的应用的全屏空间，点开大概率会切出全屏。**这是系统限制，不是缺陷**；如果实测体感不可接受，需要单独设计兜底方案，不要简单回退本次改动。
4. **收起后焦点归属**：确认没有把焦点从用户正在用的应用抢走。
5. **置顶窗口**：确认全程不会被自动收起。
6. **系统程序坞同侧**：系统程序坞在右侧时，把侧边 Dock 也切到右侧，确认它停在程序坞内侧且不影响程序坞唤出。
7. **拖动与多屏**：沿边缘上下拖动并跨屏，重启后确认仍在正确屏幕和相对高度。
8. **焦点表现**：启动、鼠标点击和键盘导航时都不出现系统蓝色焦点框；键盘聚焦条目时仍能看到克制的自定义焦点态。
